## 1. 계정 기본 보안 설정

리소스를 배포하기 전에 계정 보안 설정을 먼저 마쳤다. 계정 생성 직후 보안 설정을 소홀히 하면, 이후 그 위에 올라가는 모든 리소스의 신뢰성이 함께 흔들리기 때문이다.

진행 순서는 다음과 같다.

1. Root 계정에 MFA(가상 인증 앱)를 등록했다.
2. Terraform 전용 IAM 사용자(`terraform-deployer`)를 생성했다. 콘솔 로그인 권한은 부여하지 않고, 프로그래매틱 액세스(Access Key 기반 API 호출)만 허용했다.
3. Access Key를 발급받아 로컬 AWS CLI에 등록하고, 정상 연결을 확인했다.

> 📸 `01_root_mfa_enabled.png` — Root MFA 디바이스 할당 완료 화면 (계정 ID는 모자이크 처리)
> 📸 `02_iam_user_created_masked.png` — IAM 사용자 Access Key 발급 화면 (Access Key ID / Secret Key 모두 모자이크 처리)
> 📸 `03_aws_cli_configured.png` — `aws sts get-caller-identity` 실행 결과 (Account ID 모자이크 처리)

IAM 사용자의 콘솔 로그인 권한을 배제한 이유는, 해당 사용자가 사람이 직접 조작할 대상이 아니라 Terraform이 API를 통해 호출하는 용도이기 때문이다. 사용하지 않는 접근 경로는 애초에 열어두지 않는 것이 최소 권한 원칙에 부합한다고 판단했다.

또한 리소스를 배포하기 전에 예산 알림을 먼저 설정했다. 이번 프로젝트에서는 NAT Gateway, EC2 등 시간당 과금이 발생하는 리소스를 지속적으로 다루게 되므로, 리소스를 켜둔 채 방치할 경우 크레딧 소진 속도를 통제하기 어려워질 수 있다고 판단했기 때문이다. 월별 예산과 80% 도달 시 이메일 알림을 사전에 구성해 두었다.

## 2. 3-tier 아키텍처를 선택한 이유

Web / WAS / DB 계층을 물리적으로 분리하는 3-tier 구조는 클라우드 인프라 보안에서 가장 기본이 되는 설계 원칙이다. 이번 프로젝트의 첫 단계로 이 구조를 직접 설계하고 코드로 구현하는 것을 목표로 삼았다.

설계 원칙은 다음과 같다. **외부에서 접근 가능한 계층은 최소한으로 두고, 나머지 계층은 해당 계층을 경유하지 않으면 접근할 수 없도록 구성한다.**

### 네트워크 구조

| 계층 | CIDR | 서브넷 유형 | AZ |
|---|---|---|---|
| Web | `10.0.1.0/24`, `10.0.2.0/24` | Public | 2a, 2c |
| WAS | `10.0.11.0/24`, `10.0.12.0/24` | Private | 2a, 2c |
| DB | `10.0.21.0/24`, `10.0.22.0/24` | Private | 2a, 2c |

가용영역(AZ)을 2개 사용해 하나의 AZ에 장애가 발생하더라도 서비스가 유지되도록 구성했다. CIDR 대역도 계층별로 1번대/11번대/21번대로 구분해, 이후 로그 분석 시 IP 대역만으로 어느 계층에서 발생한 트래픽인지 빠르게 식별할 수 있도록 했다.

### 라우팅 구성

- Public(Web) 서브넷은 Internet Gateway를 통해 인터넷과 직접 양방향 통신이 가능하다.
- Private(WAS, DB) 서브넷은 NAT Gateway를 통해서만 아웃바운드 통신이 가능하며, 인바운드 접근은 원천적으로 차단된다.

즉 WAS와 DB 계층은 외부로 나가는 통신(OS 패치 등)은 가능하지만, 외부로부터 먼저 접근당할 수는 없는 구조다.

### 보안 그룹 설계 — IP 대역이 아닌 그룹 참조 방식

보안 그룹 설계 시 IP 대역을 직접 지정하는 대신, **다른 보안 그룹 자체를 source로 참조하는 방식**을 채택했다. IP 대역으로 규칙을 구성할 경우 IP가 변경될 때마다 규칙을 수정해야 하는 문제가 있기 때문이다.

- **Web SG**: HTTP/HTTPS는 전체 허용, SSH는 관리자 IP로 제한
- **WAS SG**: 8080/SSH 포트는 Web SG에서 발생한 트래픽만 허용
- **DB SG**: 3306 포트는 WAS SG에서 발생한 트래픽만 허용

이 방식으로 구성하면 Web → WAS → DB로 이어지는 접근 흐름이 코드만으로 명확하게 드러난다. 또한 이 구조 위에서 **Bastion Host 패턴**이 자연스럽게 구현된다. 외부에서는 Web 서버로만 SSH 접속이 가능하며, 이후 WAS/DB로는 Web 서버를 경유해서만 접근할 수 있다. EC2 배포 이후 이 접속 흐름을 직접 검증하고 캡처로 남길 예정이다.

관리자 IP는 유동 IP로 변경될 가능성을 고려해, 하드코딩 대신 리스트 타입 변수(`admin_ips`)로 분리했다. 접속 환경이 추가되면 리스트에 값을 추가하는 것만으로 대응할 수 있도록 구성했다.
